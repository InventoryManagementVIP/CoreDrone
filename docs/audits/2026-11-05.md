# CoreDrone engineering and security audit

**Audit date:** 2026-11-05. **Source revision:** `b13b465bf33df07f8afb04fd9cf72de901244a30`.

**Assessment:** The repository has a coherent simulation-first architecture and useful automated checks, but the current implementation is not ready for autonomous warehouse flight or production backend delivery. The most serious defects concern abort arbitration, stale health information, flight-limit configuration, and geofence enforcement. A passing nominal flight does not establish safe behavior under failure.

This is a source review and controlled software validation, not hardware flight certification. Severity reflects potential impact; findings whose exploitation depends on network reachability are identified explicitly.

## Scope, assumptions, and verification

Reviewed the 13 ROS packages, simulation and evaluation code, JSON contracts, warehouse configuration, Docker images and Compose files, Jetson/systemd deployment, dependency manifests, pre-commit configuration, and GitHub Actions workflows. The core Python inventory contains 118 files and approximately 9,271 lines, including 32 test files. These counts exclude this audit's reproduction script and generated build artifacts.

The Companion App and Supabase deployment are absent: `app/README.md` explicitly delegates them to another repository. Their authentication, database policies, API security, tenant isolation, and frontend behavior cannot be assessed here. No real vehicle, Jetson, camera, RC link, or production credentials were exercised. Hardware configuration is explicitly described as untested throughout the repository.

## 1. Architecture & Design Patterns

### What works well

- Responsibilities are divided sensibly among localization, perception, inventory, mission, safety, uplink, and flight control. The `FlightBackend` and `BackendClient` interfaces provide useful extension boundaries.
- The sim/real platform split keeps most autonomy code shared. The single warehouse layout model reduces duplication between route generation, simulation, and attribution.
- Pure control math, safety policy, attribution, and evaluation functions are separated from ROS callbacks, making focused testing practical.
- SQLite WAL, parameterized statements, a pending-record index, and a separate uplink process are appropriate for one vehicle that must operate without a network connection.
- Explicit messages, actions, schemas, ADRs, onboarding guides, and flight-test documents give the project a stronger foundation than an undocumented collection of ROS nodes.

### F01 — Critical: real-vehicle limits are overwritten by package defaults

**Evidence:** `drone/src/inv_bringup/launch/drone.launch.py:70-77,128-136`; `drone/src/inv_bringup/config/real.yaml:3-6`; `drone/src/inv_flight_interface/config/flight_interface.yaml`.

The parameter helper puts platform settings first and package settings afterward. ROS therefore overwrites the real platform's intended horizontal/vertical limits of **0.5/0.3 m/s** with **1.0/0.5 m/s**. The actual ROS parameter parser reproduced these effective values. This is a safety-sensitive precedence error, not just configuration duplication.

Relatedly, `scan.speed_mps` is parsed into the layout but is never passed to `bt.goto()` in `inv_mission/node.py:109`; its action goals use the default speed selection. A warehouse's configured scan speed consequently does not control route execution.

**Fix:** Apply package defaults, then platform overrides, then mission/site values and explicit user overrides. Assert the effective real configuration in a launch test, and propagate the layout speed into route action goals. Review all nodes for the same ordering error. The advertised top-level `params_file` also does not propagate to every included subsystem; define and test a consistent override contract.

### F02 — Critical: abort is neither protected from preemption nor confirmed

**Evidence:** `inv_flight_interface/node.py:265-272,304-306,323-325,405-419`; `inv_safety/monitor.py:115-122` (paths under `drone/src/<package>/<package>/`).

Every new action execution calls `_start()`, which preempts the current command without considering priority. While an abort is holding before landing, a valid Hover or GoTo goal can replace it. The special protection against this exists only for the velocity-topic path. The reproduction replaced an active abort with a normal hover.

The safety monitor compounds this by setting `_abort_requested=True` immediately after dispatching an asynchronous service request. It does not inspect `accepted`, exceptions, response timeout, or subsequent flight state. A rejected, lost, or later-preempted request can suppress further abort attempts until disarm.

**Fix:** Put command arbitration in one place, make abort/landing a latched safety state, and reject lower-priority commands until a deliberate reset or disarm. Track request, acknowledgement, and observed landing separately; retry with bounded backoff until the commanded safe outcome is verified. Test concurrent GoTo/hover/land requests, lost acknowledgements, rejected aborts, and pilot override.

### F03 — Critical: the safety chain does not expire all of its inputs

**Evidence:** `inv_safety/monitor.py:68-100`; `inv_flight_interface/node.py:210-235,447-454`; `inv_flight_interface/ap_dds_backend.py:100-134`; `inv_localization/adapter.py:42-48,126-147`.

After one TRACKING message, the safety monitor retains localization health indefinitely if that publisher disappears. It records no arrival timestamp for localization or corridor status. Independently, the flight interface requests the latest TF with `Time()` and does not check its age. Its control-output gate does not require fresh external navigation while airborne. A transform that was 99 seconds old still produced a usable pose in the reproduction, and a vanished TRACKING publisher still left safety at OK.

FC health is also aggregated too broadly: `/ap/time`, battery, origin, and pose messages all refresh one `last_message_s`. Continuing clock messages can hide stale armed/mode/failsafe status or a stale battery percentage. Future-dated odometry produces a negative age that `classify()` accepts as TRACKING.

ArduPilot's EKF and GUIDED failsafes offer another layer, but they do not correct the companion application's stale-state decisions or prove the timing of a safe recovery.

**Fix:** Track freshness independently for status, battery, odometry, TF, backend tracking, and corridor information. Require bounded timestamp age and monotonic sequence progression, with a small explicit future-skew allowance. Use monotonic arrival time for liveness and ROS time for measurement alignment. Add an independent flight-interface response to missing safety/localization heartbeats and test node death, partial topic loss, clock jumps, and replayed samples.

### F04 — High: a failed mission can leave the aircraft holding indefinitely

**Evidence:** `inv_mission/node.py:66,131-164`; `inv_flight_interface/node.py:247-250,498-515,590-593`.

On a behavior-tree failure, `_stop()` changes the mission state and interrupts the tree, but does not request abort or landing. The status timer continues publishing FAILED messages. The flight interface treats every status message as a healthy heartbeat and ignores its state. For example, a GoTo timeout can leave a hold target active while the mission is permanently failed; heartbeat-loss landing never triggers. The reproduction showed a FAILED message refreshing the watchdog and preserving hold.

**Fix:** Give terminal mission failure a defined safety transition: request and verify landing/abort, or use a bounded operator-recovery hold with a landing deadline. Make the flight interface validate heartbeat state and progress rather than treating any message as evidence of a healthy mission.

### F05 — High: warehouse geometry and route safety are only partially validated

**Evidence:** `inv_layout/layout.py:298-413`; `contracts/warehouse_layout.schema.json`; `inv_mission/route.py:32-62`.

The loader validates schema shape and selected invariants, but accepts shelf decks `[10.0, 0.4]` in the small warehouse: descending levels, including a deck above the rack roof. There are no complete checks for rack extent within an aisle, rack/aisle overlap, unique rack and aisle identities, vehicle footprint clearance, or the clearance of every straight route segment. A containing geofence does not establish collision-free travel.

**Fix:** Add semantic geometry validation and validate the entire route before arming, using vehicle dimensions, braking margin, ceiling/floor clearance, and configured flight limits. Invalid sites should fail before takeoff, rather than midway through a mission when the next goal is rejected.

### Deployment requirements still unresolved

**F06 — High, deployment assumption to verify: warehouse-frame registration.** The Isaac launch publishes its SLAM `map/odom` frames (`inv_localization/launch/isaac.launch.py:33-45`; `config/isaac_vslam.yaml:11-18`), while mission routes use absolute warehouse coordinates. There is no implemented or documented startup procedure that registers the SLAM coordinate frame to surveyed warehouse coordinates. Setting a geodetic EKF origin is a separate operation. If initial pose/orientation is not externally registered, TRACKING alone is insufficient to establish that route coordinates point to the intended shelves. Implement registration to surveyed tags/a persisted map and gate mission readiness on verified registration. This is a missing deployment guarantee, not a reproduced hardware collision.

**F07 — High, explicit feature gap: obstacle blocking has no effective safety behavior.** `inv_mapping/corridor_checker.py:35-50` reports UNKNOWN and `blocked=False` even when the nvblox backend is selected. `inv_safety/policy.py:73-74` raises only WARN for a blocked corridor, and `inv_mission/node.py:82-84` reacts only to `abort_requested`. Thus even a future true blocked signal does not implement the documented hold behavior. Retain a supervised, cleared-area operating scope until corridor checks and a tested hold/stop branch exist; real deployments should fail their readiness check when required collision protection is unavailable.

### Scaling assessment

The architecture is suitable for a single experimental drone and modest layouts. Multiple drones require explicit namespaces or separate secured domains, unique vehicle IDs, mission identifiers that do not collide, and per-drone backend authorization. Absolute ROS topic names and the shared default domain prevent uncomplicated fleet composition. More ROS processes alone will not solve the local queue, attribution, or mission-tree growth described in section 4.

## 2. Code Quality & Maintainability

Names and module documentation are generally clear, and formatting is consistent. Ruff passed across the reviewed tree. Explicit TODO markers are useful, especially where hardware and GPU components are not yet implemented.

The main maintenance hotspot is the 711-line flight-interface node: it combines action admission, synchronization, command arbitration, retries, TF lookup, controller logic, watchdogs, and diagnostics. `Command.kind/phase` strings and an untyped `params` dictionary allow invalid combinations that a typed command model and explicit transition table could prevent. Refactor incrementally around those safety boundaries, preserving behavior with failure-path tests.

Other concrete concerns:

- **F08 — Medium: inventory deduplication loses later evidence.** `inv_inventory/node.py:70,132-150` keys `_best` only by decoded code; `attribution.py:100-102` accepts only a strictly higher attribution-method rank. Once a label attribution is recorded, a later, better label-based correction is suppressed even if its slot or confidence differs. If barcodes represent SKUs shared across physical items, this also suppresses all but one instance per mission. Confirm whether the contract requires a unique physical-item identifier; otherwise deduplicate using an item/slot/observation identity and retain corrections/provenance. `_best` is also updated before successful persistence.
- Callback failures are handled unevenly. SQLite errors in inventory callbacks and file-write errors in `MockBackend.upsert()` can escape the node's normal recovery logic; uplink catches `BackendError`, not arbitrary filesystem/SQLite failures. Disk-full, locked-database, and export-on-shutdown errors deserve explicit health reporting and recovery. A shutdown export exception can also prevent queue closure and ROS cleanup.
- Logs are mostly human-readable strings. Add structured mission, scan, command, phase, and reason identifiers; command/telemetry ages; callback latency; disk availability; and confirmed safety transitions. Per-item INFO logging should be configurable at warehouse scale. Avoid flooding logs with every revalidation of a permanently bad record.
- Default dictionaries and YAML files duplicate configuration. Tests currently check equality, which catches drift but does not verify the effective layered configuration, as F01 demonstrates.
- Runtime code locates layouts and contracts through repository ancestors/`INV_ROOT`. This works in the committed image arrangement, but makes standalone package installation fragile. Package these resources or make an explicit, validated resource provider part of deployment.
- Minor cleanup includes unused `raw` aggregation in `inv_inventory/node.py:117-122` and the unreachable `return` following `os.execvp()` in `inv_tools/record.py:42-43`. The marked phase-2 modules are intentional stubs, rather than confirmed accidentally dead implementations.

## 3. Security Vulnerabilities

### F09 — High: network-facing control has no committed identity or authorization policy

**Evidence:** `real/jetson/compose.yaml:8-12`; `.env.example:10-12`; `real/jetson/mavlink-router.conf:3-18`; `docker/compose.yaml:44-45,61`; `inv_bringup/launch/drone.launch.py:183-190`.

The onboard stack uses host networking and the default ROS domain is zero. The repository supplies no DDS-Security keystore, enforcement setting, enclave permissions, authenticated gateway, or host firewall policy. Domain IDs separate discovery traffic but are not identities or authorization. A participant that can join this unsecured graph can invoke flight actions, spoof health/mission messages, and call the export service.

Foxglove binds `0.0.0.0`, and Compose publishes `8765:8765` on host interfaces by default. MAVLink routing enables TCP port 5760 and a broadcast GCS destination; no signing policy is configured in this repository. Reachability and any externally applied firewall, signing configuration, or authentication remain unverified. Internet exposure is not established by this review.

**Fix:** Default desktop diagnostics to `127.0.0.1:8765:8765` and use an authenticated tunnel for remote access. Define ROS enclave permissions and enable enforced DDS security where supported. Separately validate the XRCE/FC bridge's security boundary and isolate it; securing some ROS nodes does not automatically secure every bridge participant. Restrict vehicle network access and configure MAVLink 2 signing with appropriate unsigned-message rejection and key management. Signing authenticates messages; use a protected transport when confidentiality is also required. See the [ROS security design](https://github.com/ros2/design/blob/gh-pages/articles/180_ros2_dds_security.md), [MAVLink signing guide](https://mavlink.io/en/guide/message_signing.html), and [Docker port-publishing behavior](https://docs.docker.com/engine/network/port-publishing/).

### F10 — High: export service allows writes outside its export directory

**Evidence:** `inv_uplink/node.py:77-90`; `inv_uplink/export.py:38-45`; `inv_interfaces/srv/ExportCsv.srv`.

The caller controls `request.path`; it reaches `Path.open("w")` without confinement, extension validation, or no-overwrite protection. The reproduction replaced an existing file outside `export_dir` with CSV contents. The service can overwrite any file its process is permitted to write. This is a filesystem-integrity and denial-of-service issue; an arbitrary-code-execution outcome was not established. It is reachable remotely only if an attacker can access the service, as in F09.

**Fix:** Accept an export filename or opaque job ID, resolve it beneath one permitted directory, reject traversal and symlink escapes, and use exclusive/atomic output creation. Validate mission IDs before incorporating them into names. Restrict service callers and run the process with a narrow write set.

The Jetson Dockerfile does not explicitly set an unprivileged `USER`, so the effective user depends on its unverified NVIDIA base. Runtime configuration also lacks explicit capability reduction, no-new-privileges, and a read-only root filesystem. Verify the actual image user, then constrain runtime privileges while preserving the camera/serial access the hardware needs.

### F11 — Medium: barcode text can become an executable spreadsheet formula

**Evidence:** `inv_perception/code_reader.py:112-115`; `inv_uplink/export.py:31-45`.

Untrusted decoded text is copied into CSV unchanged. A barcode containing `=1+1` survived the complete export function as a formula-bearing cell. CSV quoting handles separators, but does not force spreadsheet text interpretation. The practical impact depends on the spreadsheet application's features, settings, warnings, and operator behavior; no spreadsheet-based code execution was attempted.

**Fix:** Provide a spreadsheet-safe export mode with tested text handling, preferably a format with explicit string cell types. Preserve a separate canonical machine-readable export when escaping would alter inventory identifiers. Test formula prefixes, leading control characters, delimiters, and save/reopen behavior in supported spreadsheet applications. [OWASP's CSV injection guidance](https://community.owasp.org/attacks/CSV_Injection) explains the application-dependent limitations.

### F12 — High: command inputs permit non-finite values

**Evidence:** `inv_flight_interface/node.py:252-262,308-321,634-672`; `control.py:78-109`.

Incoming velocity components, quaternions, durations, tolerances, and speed overrides do not receive comprehensive finite/range validation. Ordinary `min/max` clamping does not reliably neutralize NaN. The reproduction passed a NaN horizontal velocity through `_send()` to the backend. Firmware response is outside this source-level reproduction, but emitting invalid flight-control data is itself an unsafe interface contract.

**Fix:** Reject non-finite values and invalid quaternions before admitting commands; require documented positive bounds for speed, duration, tolerances, and configuration rates. Validate velocity frame IDs and sample ages. Add final finite-output assertions at the backend boundary and fail to an explicitly defined safe transition.

### Dependency and vulnerability-management assessment

There are useful existing controls: selected Python tools are version-pinned, several upstream sources use commit SHAs, upstream patches are documented, secret values are externalized, the Docker build context is allowlisted, and GitHub jobs generally declare limited token permissions. Parameterized SQLite and `yaml.safe_load()` are used in the inspected runtime paths. No direct SQL injection, unsafe YAML construction, committed credential, or runtime shell execution of decoded labels was identified.

**F13 — Medium: dependency reproducibility and vulnerability detection are incomplete.**

- `ros:<distro>-ros-base`, development/runtime image tags, apt/rosdep repositories, and several source tags remain mutable rather than digest/commit-locked. They do not support the documentation's broad claim that everything is pinned reproducibly.
- `docker/jetson.Dockerfile:64` and `docker/isaac-x86.Dockerfile` install unpinned `pymavlink`, unlike the dev image's firmware-matched source install. Transitive pip dependencies are not hash-locked.
- `docker/dev.Dockerfile:44-48` downloads and extracts `just` without an explicit checksum verification step.
- Actions use major-version tags rather than immutable commit SHAs. The workflows contain no dependency vulnerability scan, image CVE gate, SBOM generation, or visible automated dependency-update configuration.
- Image publication is not gated on the build/test and simulation workflows: `.github/workflows/docker-publish.yml` independently publishes on matching main pushes. Nightly publication and mission validation also run as separate jobs without a validation dependency.

**Fix:** Record exact image digests and build dependency inventories, align dev/vehicle firmware-facing dependencies, verify downloaded artifacts, pin Actions by reviewed SHA, generate SBOM/provenance, and scan both Ubuntu/ROS packages and pip/native components. Apply a documented exploitability and patch SLA instead of blindly upgrading firmware-facing dependencies. Promote a tested image digest after required checks pass. [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) supports immutable action pinning.

Observed cached versions included MAVProxy 1.8.71, future 1.0.0, dronecan 1.0.27, pymavlink 2.4.49, Ubuntu PyYAML 6.0.1-2build2, jsonschema 4.10.3-2ubuntu1, and zxing-cpp 2.2.1-3. These are inventory observations, not a current CVE determination; Ubuntu backports and the installed native libraries must be included in any advisory assessment.

## 4. Performance & Efficiency

### F14 — Critical: acceleration limiting can undo the geofence filter

**Evidence:** `inv_flight_interface/node.py:649-665`; `control.py:53-61,99-109`.

The output path zeroes outward velocity at the fence/ceiling, then slews from the previous setpoint. The slew calculation restores some of that outward velocity. With position on the fence boundary, previous outward speed 1.0 m/s, a 50 ms tick, and the default 1.5 m/s² acceleration limit, the final emitted speed was **0.925 m/s outward**. The same ordering affects the ceiling. The configured FC geofence is disabled in `real/flight_controller/params/common.parm:67`.

**Fix:** Enforce a final safety constraint after normal control smoothing and incorporate braking-distance/latency margins before the boundary is reached. Reordering alone cannot prove a physically collision-free stop. Verify bounds across speed, control jitter, stale pose, saturation, and takeoff/landing modes; add an independent FC boundary where feasible.

### F15 — High: bad queue records can permanently starve good records

**Evidence:** `inv_inventory/queue.py:55-73`; `inv_uplink/node.py:55-75`.

The pending query always selects the oldest unsynced batch. Contract-invalid records are marked failed but remain eligible immediately. Once those records fill a batch, every sync reselects them and no later valid record is uploaded. With batch size two, two invalid old records blocked a later valid record over repeated sync attempts. A batch of 50 invalid records causes the same behavior under the default configuration.

**Fix:** Validate at ingestion, add explicit queued/retry/dead-letter states, quarantine permanent contract failures, and schedule transient failures with backoff and a next-attempt timestamp. Test mixed valid/invalid queues and sustained outages. Publish poison-record count and oldest-pending age, not just queue length.

### F16 — Medium: runtime resource use grows with history and layout size

**Evidence:** `inv_inventory/queue.py:46-87`; `inv_inventory/node.py:89-120`; `inv_inventory/attribution.py:54,75-76`; `inv_layout/layout.py:209-232`; `inv_mission/node.py:107-129,170-180`; `inv_uplink/backends.py:37-53`.

| Hot path | Consequence | Recommended change |
|---|---|---|
| One SQLite commit per scan, synchronous in inventory callback; 10-second lock timeout | Disk/lock contention stalls detection processing and its callback group | Bounded writer queue, small transaction batches, explicit disk/lock health |
| `records().fetchall()` and full JSON materialization for every export | Export memory and latency grow with all stored missions; export blocks uplink callbacks | Cursor-based streaming/pagination, mission/date indexes, export worker |
| Full `COUNT(*)` diagnostics each second and no retention/compaction policy | Work increases with retained history; eventual disk exhaustion | Incremental counters, retention after durable sync, capacity alerts |
| TF lookup and 100 ms timeout per detection; tag adapter similarly waits per tag | Missing transforms multiply blocking time for one image | Resolve once per frame/stamp, bounded waiting, report pose-missing rates |
| Linear nearest-slot search for each fallback attribution | O(detections × slots) lookup work | Cache slot/rack maps; spatial index for large layouts |
| Rack lookup repeated for each slot during attribution setup | Repeated layout scans as racks and slots grow | Build immutable indexes once |
| Whole behavior tree/action clients constructed for every waypoint and full-tree progress scans | Startup, graph entities, memory, and status work grow with route length | Reuse one action client per action type; execute waypoints through a route iterator/subtree |
| `_pending`, `_best`, and mock backend `rows` have no explicit count/byte ceiling | High-rate or malformed detections and long deployments can exhaust memory | Bound input sizes/backlogs, expire state, use persistent idempotency rather than unlimited mock memory |

The process split protects the flight loop from direct network waits, which is good. Shared Jetson CPU, memory, disk, and DDS transport still require resource budgets and measured p95/p99 callback/control-loop latency. A network timeout parameter alone is not sufficient when the HTTP implementation is added: keep network work off the callback path used for diagnostics and service responsiveness.

No ORM-style N+1 query problem was found. The analogous costs here are repeated TF requests, per-record transactions, linear geometry lookups, and unbounded export/history work. Existing schema-validator caching is appropriate; caching stale safety data would be harmful.

## 5. Testing & CI/CD Readiness

The project has credible foundations: amd64/arm64 build matrices, lint and contract jobs, ROS launch tests, a PR SITL smoke path, a nightly scan mission, timeouts, and failure log artifacts. Tests cover control math, frame alignment/time conversion, attribution, queue concurrency/idempotency, geometry, QR decoding, and basic startup. This audit observed the selected unit and launch suites passing.

**F17 — High: safety behavior lacks targeted failure-path coverage.** Flight-interface launch coverage chiefly verifies that a node without an FC publishes disconnected state (`test_flight_interface_launch.py`). The safety launch test verifies a non-OK status with no flight interface; it does not test abort acceptance/retry, lost localization after TRACKING, or actual command arbitration. Several tests assert that defaults equal YAML; that does not establish real deployment behavior.

Add regression tests for F01-F05, F10-F12, F14-F15. A fake `FlightBackend` should drive the actual command state machine through retries, delays, partial telemetry loss, disarm, pilot takeover, action cancellation, and clock resets. Add a smaller set of SITL fault-injection tests to verify firmware interaction and recovery timing. Mock behavior should include rejection, timeout, partial acceptance, process restart, and filesystem failure, rather than only probabilistic network failure.

**F18 — High, explicit delivery gap: production uplink is not implemented.** `HttpBackend.upsert()` always raises `BackendError` (`inv_uplink/backends.py:72-76`). The real platform defaults to `mock`, which marks rows synced after local mock acceptance. Switching backends later will not automatically make those rows pending again. The project can demonstrate local collection/export, but cannot currently guarantee backend delivery. Complete and test authenticated idempotent HTTP delivery with the app team, scoped permissions, durable acknowledgement semantics, and destination-aware sync state before production collection depends on it.

Additional CI/deployment gaps:

- Nightly mission quality is not gated: `sim/tests/test_sim_mission.py:105-108` requires only at least one decoded item. Zero correct-slot attribution or a major recall regression can still pass. Establish explicit recall, false-read, attribution, mission-duration, and safe-landing thresholds on known layouts.
- There is no measured branch-coverage gate for the safety/control state machines. Add targeted branch requirements for those modules; do not substitute one arbitrary repository-wide percentage for failure-mode coverage.
- GPU/Isaac and Jetson images are not built/tested by the committed hosted CI. Base tags are explicitly UNVERIFIED in `docker/.env:15-21`; calibration noise values, hardware frames, and sensor/RC settings remain placeholders. Add hardware-in-the-loop validation and a supported GPU runner or a documented release-blocking manual result.
- The first smoke invocation returned exit code zero even though the localization adapter raised a `RuntimeError` and exited with code 1 during intentional teardown. This was observed after the nominal flight, not established as an in-flight failure. Add shutdown tests with expected process exit codes and orderly executor cleanup; the current test has no post-shutdown exit assertions.
- There is no clean-build/arm64 result from this audit. The existing workflows configure those jobs, but their execution history, branch protection, required checks, and reviewer enforcement were not inspected.
- CODEOWNERS says its teams still need to be created (`.github/CODEOWNERS:2`). Confirm that ownership and required review are enforced. Listing multiple owners on a path does not by itself prove independent sign-off by both teams.
- The onboard service supervises Compose, not individual ROS node health. A critical node can exit while other children keep the container alive; the launch configuration has no corresponding readiness/liveness supervision. Define a policy that reports the failure, reaches a safe flight state, and recovers only when appropriate. Avoid automatic restarts that could re-arm or reboot during flight.
- Flight-test documentation should match hardware reality: the checklist still asks for EKF source-set-2 optical-flow takeover, while `real.parm:21-25` explicitly disables that unavailable fallback.

## 6. Prioritized Recommendations

These priorities are implementation order, not a claim that every issue is remotely exploitable. Close the critical safety defects before treating successful nominal simulation as permission for autonomous hardware testing.

### Critical (Security/Blockers)

| Order | Action | Acceptance evidence |
|---|---|---|
| 1 | Latch abort/landing and verify request acceptance and actual safe outcome (F02) | GoTo/hover/velocity cannot preempt safety recovery; rejection/timeouts retry; pilot override remains authoritative |
| 2 | Enforce freshness throughout the flight/safety chain (F03) | Killing each health publisher and stopping individual FC topics triggers the defined response within a measured bound |
| 3 | Correct parameter precedence and route-speed propagation (F01) | Real launch reports 0.5/0.3 m/s and site scan speed is honored; explicit overrides behave predictably |
| 4 | Repair geofence output constraints and braking margins (F14) | Boundary/ceiling tests never emit forbidden output after smoothing; SITL confirms stopping distance under jitter |
| 5 | Constrain export paths and isolate command access before shared-network deployment (F09-F10) | Export cannot overwrite an existing out-of-root file; unauthorized participants cannot issue control/export requests |

### High (Performance/Architecture)

| Order | Action | Acceptance evidence |
|---|---|---|
| 6 | Define terminal mission recovery and reject malformed commands (F04, F12) | Failed missions reach bounded hold/land; NaN/Inf and invalid goals are rejected before FC output |
